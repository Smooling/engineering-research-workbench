### F-01 · BibTeX 导出为空或使用旧引用

**相关位置**：`app/perf_index_graph.py:240` 的 `export_bibtex()`；其第 258 行从正文提取 BibTeX。统一文献读取逻辑位于 `app/store.py:339`。

**复现 A：仅元数据保存引用。**

1. 通过 `POST /api/docs` 创建文献，`kind` 为 `literature`，`bibtex` 为有效引用；正文不包含 BibTeX 代码块。例如：

   ```json
   {
     "kind": "literature",
     "title": "功能测试文献",
     "bibtex": "@article{qa2026,title={Synthetic Study},year={2026}}",
     "body": "# 阅读笔记\n\n合成测试资料。"
   }
   ```

2. 将返回的文档 ID 放入 `POST /api/literature/export-bibtex` 的 `ids` 数组。
3. 查看返回值及导出文件。

**实际结果**：本轮 12 篇均有有效元数据引用的文献批量导出，返回 HTTP 200、`ok: true`，但 `count: 0`、`content: ""`，生成空文件。

**复现 B：新旧引用冲突。** 创建文献时，元数据 `bibtex` 为 `@article{current_new,title={New}}`，正文保留旧的 fenced BibTeX `@article{legacy_old,title={Old}}`，然后导出。

**实际结果**：返回 `count: 1`，内容却是 `legacy_old`。

**预期结果**：与当前文献读取规则一致，优先导出元数据中的 BibTeX；仅在旧文档缺少该字段时回退正文。用户主动清空字段时，不应重新导出旧正文引用。

**原因**：导出器直接匹配正文中的 BibTeX 代码块，没有使用文献读取器已实现的元数据优先规则。

**修复建议**：复用统一文献读取结果；区分字段不存在与字段为空。导出响应补充选中数、导出数及缺失项，避免部分/全部缺失时只返回笼统成功。

**验收标准**：

- [x] 仅有元数据 BibTeX 的文献能够导出；本轮 12 篇样例应导出 12 条。
- [x] 只有旧正文代码块且无元数据字段的文献保持兼容。
- [x] 元数据与正文冲突时，导出元数据中的引用。
- [x] 元数据显式为空时，不回退为旧正文引用。
- [x] 混合批次、多行引用、中文字段及缺失引用均有明确结果。

**证据**：[空导出响应](review-evidence-2026-10-21/bibtex-result.json)、[旧引用导出复现](review-evidence-2026-10-21/supplemental-evidence.json)、[真实接口测试清单](review-evidence-2026-10-21/api-results.json)。

### F-02 · 概览项目里程碑数显示为 0

**相关位置**：`web/app.js:554` 的 `projectPulseCard()`；后端统计位于 `app/perf_index_query.py:420` 和第 444 行。

**复现步骤**：

1. 创建项目并关联 12 个里程碑，其中 6 个完成、6 个未完成。
2. 打开项目页，核对该项目的里程碑数量。
3. 打开概览，查看“项目推进”中的同一项目。
4. 对照 `/api/project-records`、`/api/dashboard` 与甘特图。

**实际结果**：项目页和项目记录接口显示 12 个里程碑，甘特图共显示 12 个；dashboard 返回 `open_milestones: 6`，概览项目卡却显示 **0 里程碑**。本轮两个共享这批里程碑的项目均出现该问题。

**预期结果**：同一指标在界面和接口间保持一致。展示总量应为 12；展示待完成量应为 6，并明确标注“待完成节点”。

**原因**：后端返回 `open_milestones`，前端读取不存在的 `milestones`，再通过 `|| 0` 显示为 0。

**修复建议**：确定总量/待完成量的产品口径后统一字段和标签；保留多项目共享资料的计数规则。增加使用真实 dashboard 响应的界面集成检查，避免模拟数据使用前端期望字段而掩盖接口不一致。

**验收标准**：

- [x] 有里程碑的项目不再因字段缺失显示为 0。
- [x] 无里程碑、全部完成、部分完成三种情况均正确。
- [x] 项目页、概览、甘特图的数量差异均能由明确口径解释。
- [x] 多项目关联不会遗漏节点；不把各项目数量之和当作全局去重总量。

**证据**：[项目与概览接口对照](review-evidence-2026-10-21/supplemental-evidence.json)、[项目页截图](review-evidence-2026-10-21/projects-wide-light.jpg)、[概览截图](review-evidence-2026-10-21/overview-wide-light.jpg)。

### F-03 · 待办异常输入可以直接保存

**相关位置**：`app/todos.py:45` 的 `create()` 与第 66 行的 `update()`。

**复现步骤**：向 `POST /api/todos` 分别提交：

```json
{"title":"   "}
{"title":"无效日期待办","due":"2026-99-99"}
{"title":"无效优先级","priority":"unexpected"}
```

随后读取待办列表并查看概览。

**实际结果**：三个请求均成功写入。第一条标题变为空字符串，第二条保存非法日期，第三条在界面直接显示 `unexpected` 优先级。

**预期结果**：非法输入返回 400 和明确字段错误；不新增异常记录。正常的默认值或空日期行为需单独定义。

**原因**：创建函数只转换字符串或填默认值；没有对 trim 后标题、有效日历日期和优先级范围进行统一校验。代码检查发现更新函数也直接接受这些字段；本轮三个异常请求实测的是创建路径，更新路径仍需补充独立回归。

**影响**：服务端调用方可以绕过页面限制写入异常数据，任务列表和日期/优先级相关行为缺少可靠数据前提。本轮未实测所有导入和同步路径，不能据此断言它们必然触发同一问题。

**修复建议**：创建和更新共用校验器。标题 trim 后非空；日期合法或符合明确空值策略；优先级来自允许集合；完成状态类型一致。历史异常数据应提示修正，避免静默删除。

**验收标准**：

- [x] 三个异常样例在创建路径均返回 400，数据文件不新增记录。
- [x] 更新路径同样拒绝异常值，并保留原记录。
- [x] 合法日期、允许优先级和正常完成/恢复操作仍通过。
- [x] 缺省值、显式空值、字段类型错误有一致处理规则。
- [x] 失败请求不会产生成功的业务写入或活动记录。

**证据**：[真实接口检查结果](review-evidence-2026-10-21/api-results.json)，检查名称为 `validation: todo blank title rejected`、`validation: todo invalid date rejected`、`validation: todo invalid priority rejected`。

### 修复内容与产品口径

- **F-01**：`export_bibtex()` 复用统一文献读取器，元数据优先、缺少字段时兼容旧正文、显式清空时不回退。保留 `count/content/path/ok`，新增 `selected_count/exported_count/missing`；缺失项区分无引用、条目不存在、非文献和读取失败。重复 ID 按唯一文献计数，文件名加入微秒以免同秒覆盖。当前文献页“导出引用”显示选中数、导出数和可展开的缺失清单；全部缺失时提示补充引用，不下载空文件。
- **F-02**：概览直接使用真实接口的 `open_milestones`，标签明确为“待完成节点”。项目页和计划视图保留总量口径；共享节点分别计入关联项目，全局仍去重。工作台 UI 夹具也改用后端实际字段，新增真实 HTTP 响应到页面的集成检查。
- **F-03**：创建与更新共用 `todos.validate_payload()`，在业务写入前完成校验；错误返回 HTTP 400，消息包含字段名。更新合并后也校验完整记录，历史非法值需修正后再保存，记录不会被静默删除。输入策略如下。

| 字段 | 创建时省略 | 显式空值及类型规则 |
|---|---|---|
| `title` | `新任务` | 必须为 trim 后非空的字符串；空字符串、空白、null 和非字符串拒绝 |
| `due` | 当天日期 | `""` 或 null 清空日期；其余必须为有效日历日期，且严格符合 `YYYY-MM-DD` |
| `priority` | `普通` | 仅允许 `普通/紧急/高/低`；空字符串、null 和其他类型拒绝 |
| `done` | false | 仅接受 JSON 布尔值；数字、字符串和 null 拒绝 |

- **T-01**：self-check 改为检查 `agent-client.js` 中的发送接口及其页面加载关系。
- **T-02**：Agent UI 等待本次特定用户消息之后的新错误和任务结束，再核对新增请求及片段数量，避免上一轮相同错误误命中。
- **T-03**：引用跳转检查改为当前的 `openByDocument` 入口，并核验目标文献 ID。
