> 依据：2026-10-09 对当前分支（`feature/slim-workbench-v261009`）代码与 `Workspace/` 数据的实测。
> 配套文档：[docs/REFACTOR_PLAN.md](REFACTOR_PLAN.md)（精简与插件化实施方案）。
> 本文回答三个问题：**这个工具是干什么的**、**哪些功能是核心**、**哪些应该是插件**。

## 0. 一句话定位

> **单人、本地优先的科研知识与文献整理平台**：把研究过程中产生的笔记 / 灵感 / 日志 / 实验 / 总结 / 里程碑 / 文献，沉淀成可检索、可互链、可汇总的 Markdown 知识库；在同一界面里完成**文献梳理与阅读**、**数据与报告留档**、**AI 辅助整理**。

Markdown + frontmatter 是唯一事实来源，SQLite 索引是可重建派生物；除显式调用外部服务（LLM / RSS / 天气）外，数据不出本机。

**明确不做的三件事**（边界，用于挡掉功能蔓延）：

| 不做 | 原因 |
| --- | --- |
| 多用户协作 / 权限 / 云同步编辑 | 单用户本地优先；协作靠 Syncthing 同步 `Workspace/` 即可 |
| 实验数据采集与分析系统（LIMS / ELN） | 不做采集、不做统计与绘图引擎；分析交给 Python/R 等外部工具 |
| 文献管理器替代品（Zotero / EndNote） | 不做云端文献库、不做 Word 引用插入 |

## 2. 功能分层

分层只有**两类机制**：**核心**写死在代码里、始终可用；**其余一切都是插件**（走同一套 manifest / 注册表 / 隔离机制）。插件再按两个轴分档：

| 档 | 谁维护 | 是否随包 | 默认状态 | 名字 |
| --- | --- | --- | --- | --- |
| 官方插件 | 本项目 | 随包发布 | **默认开**（设置里可关） | **附属功能** |
| 可选插件 | 本项目或第三方 | 不随包 / 按需安装 | **默认关** | **插件** |

> **「附属功能本质上也是插件」**：它不是一个特权层，只是「由内核作者维护、默认帮你打开」的那一档。因此 —— 附属功能必须遵守与插件完全相同的隔离不变量（REFACTOR_PLAN §6.4），核心也必须能在**所有附属与插件全部关闭**时完整跑通（§2.1 的运行不变量）。

### 2.1 核心功能（Core：零插件即可跑完整闭环）

| # | 核心功能 | 为什么是核心 | 现有实现 |
| --- | --- | --- | --- |
| C1 | **条目与知识模型**：7 类条目 CRUD、命名/字段契约、状态机、回收站、原子写 | 直接读写科研数据结构本身 | `store.py`(1190 行)、`kb_naming.py`、`workspace.py` |
| C2 | **组织**：项目、待办、科研活动日志 | 数据的一致性载体（归属、留痕） | `projects.py`、`todos.py`、`activity.py` |
| C3 | **检索与汇总**：派生索引 + 中文 FTS + 关系解析（wikilink/typed）+ 全局搜索 + 项目/阶段汇总 + 导出（Markdown 知识包 / BibTeX） | 「梳理与汇总」的必经环节 | `perf_index_*`、`indexer.py`、`store.export_bibtex`、`/api/graph/bundle` |
| C4 | **界面壳**：单页导航 + 列表/详情/编辑器 + Markdown 预览 | 一切功能的入口 | `web/index.html`、`app.js`、`styles.css` |
| C5 | **文献梳理**：文献条目 + PDF 附件登记 + 阅读状态 + 元数据补全 + BibTeX 导入导出 + 与知识条目互链 | 你的用途 ②，且已重度使用（67 条 / 56 篇） | `literature.py`(830 行)、`library.json` |
| C6 | **文献阅读（v261009.14 起改为附属插件）**：PDF 打开/翻页/缩放/跳页 + 批注（高亮/下划线/框选/墨水/便签）+ 批注存储 | 用途 ②；**2026-10-10 你的决定（反转旧决定）**：**整个 PDF 阅读工作区拆成插件**，只有启用该插件才能使用阅读区。内核保留文献**数据与文件服务**（`literature.py` 830 行、`library.json`、`/api/literature/*`、PDF 与 `Annotations/`），以及文献**列表/元数据条目页**（与笔记/灵感共用 `renderDocsPage`）。理由：关掉插件应让能力真正消失（只搬「笔记 tab」这种 UI 收益太小） | `literature.py`(830 行)、`/api/literature/<id>/pdf`、`Annotations/`；阅读 UI 见 + `plugins/literature-reader/` |
| C7 | **AI 基础**：对话（SSE 流式）+ **4 个知识库工具**（检索/读取/建档/更新，写一律走草稿确认）+ 上下文注入（当前条目/选区）+ 模型接入最小面 | 用途 ③；**精确边界见 §5** | `agent.py`(1004 行)、`agent_tools.py`(420 行) |
| C8 | **数据留档（最小）**：实验条目承载「配置与参数 / 数据与口径 / 结果 / 留档路径」，数据文件放 `Projects/<项目>/{Data,Results,Figures}` 并由条目引用 | 用途 ① 的「数据」底线：**登记与关联，不做分析** | `experiment` kind + 项目目录骨架（当前全空） |

**核心的运行不变量**：这 8 项全部可用时，即使一个插件都没装，平台依然能「录入 → 组织 → 检索 → 汇总导出」跑通，且数据完整。

| 日历 / 提醒（里程碑 due） | 时间管理 | 低 |

### 2.4 判定规则（以后新功能该放哪层）

1. **直接读写科研数据结构？**（条目 / 项目 / 待办 / 活动 / 索引 / 关系）→ 否则不进核心；
2. **去掉它，数据会失去一致性或不可恢复？**（校验、原子写、回收站、导出）→ 否则不进核心；
3. **是「录入 → 组织 → 检索 → 汇总/导出」闭环的必经环节？** → 否则不进核心。
4. 补充：**改变数据模型（新增 kind / 新字段）的功能**只能通过契约扩展机制接入，不得让核心为某个插件特判。

三条都不满足 → 就不是核心，**一律做成插件**；再按两个轴分档：属科研主线、官方维护、建议随包 → **附属（默认开）**；与科研数据无强耦合，或第三方/实验性 → **插件（默认关）**。

## 5. AI 基础功能的边界（专项定义）

**原则**：AI 的核心价值是「**在本地知识库上问答与沉淀**」——**读得到**（检索 + 读全文）、**写得回**（经用户确认落盘）、**知道你在看什么**（上下文注入）。凡不服务这条闭环、或引入额外依赖与风险的部分，一律插件化。

### 5.1 核心（不可关，零插件可用）

| # | 能力 | 精确边界 | 现状实现 |
| --- | --- | --- | --- |
| A1 | 对话内核 | 会话创建/读取/删除 + SSE 流式 + 出错与中断处理 | `agent.py` `send_message` / `_stream_chat` |
| A2 | 上下文注入（**机制**） | 把「当前条目正文 + 用户选区」拼进系统提示 | `agent._page_context` |
| A3 | 只读知识工具（2 个） | `kb_search`（先查重再动手）、`kb_read`（读全文） | `agent_tools.py` |
| A4 | 写入工具（2 个）+ 草稿确认流 | `kb_create_entry`、`kb_update_entry`，**固定 confirm 模式**：AI 只产草稿，用户点确认才落盘，拒绝即丢弃 | `agent_tools.save_draft` + `/api/agent/drafts/<id>/confirm\|reject` |
| A5 | 模型接入最小面 | 一份 provider（`base_url` / key / 模型 / 超时）+ 请求预设 + 连通性测试 | `config.py` profiles/presets、`/api/agent/test` |
| A6 | 会话与引用存储 | 会话落 `System/AgentChats/`；`refs` 手动引用本地条目 | `agent.py` 会话文件 |

> **边界铁律**：核心 AI 的工具集合**只有 4 个**，且核心**不含任何自动改库路径**——写必须经用户确认。这样「AI 会写坏库」在架构上就不可能发生。

**工具的扩展路径**（都不进核心）：默认只开上面 4 个，其余按来源分三种——① **插件注册的工具包**（`p_<id>__<tool>`，如官方 `tools-kb-admin` / `tools-ws-ops`，直接复用 `mcp/` 已有的 25 个工具，不重写）② **外部 MCP 服务器**（在 `config/mcp.json` 声明 `mcpServers`，工具名加 `mcp_<server>__` 前缀；默认关，启用需人工确认）③ 插件自带工具。完整机制见 [docs/PLUGIN_SPEC.md](PLUGIN_SPEC.md) §8。

### 5.2 附属（官方随包插件，默认开）

| 能力 | 为什么不算核心 |
| --- | --- |
| 人设系统（reader / executor / archivist + 自定义） | 本质是**工具白名单策略**，不改变「能不能问答」；核心固定用那 4 个工具 |
| `direct` 直写模式（免确认） | 提效但绕过人工复核的风险开关 |
| 悬浮球助手 | 只是入口形态；机制（A1/A2）在核心，入口做成插件 |
| 阅读区 AI 助手（翻译/总结/整理/润色 + ≤12 个自定义动作） | 依赖文献阅读视图，属「阅读增强」 |
| 阅读页正文注入 + 术语建档流水线（archivist SOP） | 依赖 PDF 文本提取与建档 SOP |
| 多模态（截图附图） | 额外依赖与成本，非问答必需 |
| 工具轨迹可视化（耗时时间线） | 观测性 |
| 会话归档 / 历史回看 | 会话管理增强 |
| 用量计费仪表盘 | 观测性 |
| `lit_context` / `lit_note_write`（2 个文献工具） | 依赖文献侧；随「文献阅读 / 文献上下文」插件一起装 |

### 5.3 插件（默认关）

- 语义检索工具 `kb_retrieve`（RAG，独立进程 + 92 MB 权重 + 69 MB 向量库）
- **官方工具包**（把已有 MCP 工具按主题打包，勾选即用）：`tools-kb-admin`（体检/改名/改 kind/删除）、`tools-ws-ops`（项目/待办/索引/图谱/导出）
- **外部 MCP 服务器接入**（`config/mcp.json`；默认关，启用时展示能力并需一次人工确认）
- 未来候选：自动摘要 / 每日回顾、批量建档、知识图谱问答、本地模型（Ollama）接入、语音输入

### 5.4 一句话

> 核心 AI = **一个能读你的库、能出草稿等你点头的对话窗**。人设、直写、悬浮球、阅读助手、多模态、术语流水线、轨迹时间线、计费、语义检索 —— 全部是可增删的插件。
