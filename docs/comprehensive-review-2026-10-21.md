## 已确认的功能问题

### P1：BibTeX 导出忽略元数据，可能为空或导出旧引用

定位：[app/perf_index_graph.py](../app/perf_index_graph.py) 的 `export_bibtex()`（约第 240 行）；文献读取逻辑见 [app/store.py](../app/store.py)（约第 339 行）。

复现一：创建 12 篇文献，每篇 frontmatter 都有有效 `bibtex`，正文为研究笔记、不含 BibTeX 代码块。向 `/api/literature/export-bibtex` 提交这 12 个文档 ID，返回 HTTP 200、`ok: true`，但 `count: 0`、`content: ""`，输出空文件。

复现二：frontmatter 为 `@article{current_new,title={New}}`，旧正文保留 `@article{legacy_old,title={Old}}`。导出得到的是 `legacy_old`。

原因：导出器直接解析 Markdown 正文中的 fenced BibTeX；未读取现在作为真值的 frontmatter。影响论文引用的正确性，优先级高于视觉改进。

建议：优先使用与文献界面相同的文档读取结果；仅在旧文档确实没有 `bibtex` 字段时回退正文，明确区分“字段缺失”和“用户主动清空”。返回选中数、导出数、缺失/无效项，避免空导出仍表现为完整成功。

验收：仅元数据、仅旧正文、两者冲突、主动清空、批量混合与中文/多行 BibTeX 均覆盖；输出键与当前界面显示一致。

### P2：概览项目里程碑数量恒为 0

定位：[web/app.js](../web/app.js) 的 `projectPulseCard()`（约第 556 行）及 [app/perf_index_query.py](../app/perf_index_query.py) 的 dashboard 聚合（约第 420–444 行）。

复现：同一项目在项目页有 **12 个里程碑**，其中 **6 个未完成**；甘特图完整显示 12 个，概览“项目推进”却显示 **0 里程碑**。两个共享这批里程碑的项目均如此。

原因：后端提供 `open_milestones`，前端读取不存在的 `milestones` 并回退为 0。

建议：先明确指标口径。展示总量就返回并读取 `milestones`；展示未完成数就读取 `open_milestones` 并标注“待完成节点”。共享项目计数保留现有多项目语义。增加真实 dashboard 响应到 UI 的集成断言，覆盖 0、非 0、全完成和多项目。

### P2：待办接口缺少统一输入校验

定位：[app/todos.py](../app/todos.py) 的 `create()` 与 `update()`（约第 50、74 行）。

向 `/api/todos` 分别提交以下输入，均被成功保存，并在概览显示：

```json
{"title":"   "}
{"title":"无效日期待办","due":"2026-99-99"}
{"title":"无效优先级","priority":"unexpected"}
```

结果分别是空白任务、非法日期和直接展示 `unexpected` 的优先级标签。正常页面的输入限制不能替代服务端校验，导入、同步和其它调用方同样需要一致规则。

建议：创建与更新共用校验器；标题 trim 后非空、日期为有效日历日期或明确允许的空值、优先级来自白名单、done 类型一致。非法输入返回 400，原记录不变。历史异常数据先标记、提示修正，避免静默删除。

## 性能结果

独立合成工作区：3,000 篇 Markdown、9,000 条图关系；冷初始化一次，热操作各 5 次，以下为中位数。此处测量后端函数耗时，不代表整页浏览器完成时间。

| 操作 | 耗时 |
|---|---:|
| 索引冷初始化 | 1,993 ms |
| 50 条文档分页 | 5.02 ms |
| 文档按 ID 打开 | 3.68 ms |
| 全文搜索 | 37.00 ms |
| 概览聚合 | 47.63 ms |
| 初始 300 节点图查询 | 18.59 ms |
| 单文档保存及索引更新 | 27.87 ms |

这个量级下后端响应较好，当前优化应更多关注界面比例、阅读与功能正确性。未据此推断万级全文 PDF、超大单文件、弱机器或真实模型调用表现。
