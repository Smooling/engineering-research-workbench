## 四、新发现与复现

### R-01 · P2：旧计划表单保存会静默覆盖较新的日期

这是数据正确性问题，建议在下一轮优先处理。

**实际浏览器复现**：

1. 甘特图打开“里程碑-阶段-活动”，表单读取截止 `2026-11-15`。
2. 独立 HTTP 客户端将同一条目的截止改为 `2026-11-29`，回读确认成功。
3. 旧甘特图中仅将进度改为 `64.5`，点击“保存计划”。
4. 界面显示“计划已保存”；回读文件及接口，截止变回 `2026-11-15`，进度为 `64.5`，没有冲突提示。

另外，双客户端 API 场景中，新截止 `2026-11-28` 也被旧快照静默回退。

**原因**：`web/milestone-gantt.js:129–134` 每次提交开始、截止、进度和状态的完整表单快照；计划保存没有携带服务端校验的修订号。`app/perf_index_runtime.py` 的文档更新路径也没有为此提供原子版本比对。

**修复与验收**：

- 计划接口返回包含排期元数据的 revision，保存时在写锁内校验 `expected_revision`；不能只比较正文哈希，或只依赖秒级更新时间。
- 前端尽量提交实际改动字段，冲突时保留用户输入，展示本地值和当前值，允许重新载入后合并。
- 两个窗口分别改日期/进度不得导致未修改字段回退；同字段竞争必须明确拒绝或由用户选择；正常保存仍保留正文。
- 覆盖同秒连续修改、Agent 草稿与手工排期竞争、同步刷新后旧表单保存。

证据：[浏览器并发保存回读](retest-evidence-agent-planning-2026-10-21/gantt-ui-concurrency.json)、[旧表单保存截图](retest-evidence-agent-planning-2026-10-21/gantt-stale-save-wide.jpg)、[API 双客户端复现](retest-evidence-agent-planning-2026-10-21/deep-results.json)。

### R-02 · P2：完成状态别名在不同模块中含义不一致

**复现**：通过真实文档接口创建状态为 `已完成`、截止为 `2026-10-01` 的里程碑，单独关联“完成别名项目”。

**实际结果**：甘特图“已完成”筛选包含该条目，显示“完成 · 100%”，不算逾期；dashboard 却返回该项目 `open_milestones: 1`。

**原因**：甘特图在 `web/milestone-gantt.js:14` 将 `完成/已完成` 都视为 done；`app/perf_index_query.py:420` 只排除原始字符串 `完成`。标准状态的上轮修复有效，这个问题针对外部写入或旧资料中的兼容别名。

**修复与验收**：提供共享状态分类，供聚合、筛选、逾期判断和图表使用；保留需要的原始显示标签或自定义状态。`完成` 与 `已完成` 在已完成数、待完成数和逾期数上必须一致；未识别状态应有明确规则，不能各模块自行猜测。

证据：[状态文档与 dashboard 原始结果](retest-evidence-agent-planning-2026-10-21/supplement-results.json)、[甘特图完成筛选](retest-evidence-agent-planning-2026-10-21/gantt-completed-alias-wide.jpg)。

### G-01 · 高优先级能力补齐：Agent 还不能操作结构化排期

**测试输入**：要求创建开始 `2026-11-01`、截止 `2026-11-15`、进度 `35%`、状态“进行中”的阶段计划；合成模型同时提供了相应工具参数。

**实际结果**：创建草稿可审批落盘，但草稿参数只保留类型、标题、正文、标签和项目等；条目日期落为默认当天 `2026-10-21`，开始为空、进度为空、状态为“计划”。日期要求虽然仍写在正文，甘特图显示当天单一节点，阶段计划数量为 0。

**定位**：`app/agent_tools.py:366` 的 `kb_create_entry` schema 没有排期字段；第 187 行实现构造 payload 时也不接收这些字段。`kb_update_entry` 同样主要操作正文，不能承担现有计划的结构化排期更新。

**定性**：这是当前工具契约的能力边界，不是声称所有真实模型必然提交了错误参数。即使模型理解日期，现有工具也无法完整执行“安排到甘特图”的任务；当前未知参数被忽略还会削弱失败提示。

**建议与验收**：

- 增加明确的计划读取/创建/更新工具，或扩展现有工具 schema；包含 `start_date/due/progress/status/projects`，复用手工编辑相同的日期与进度校验。
- 写入继续经过草稿确认，预览“字段旧值 → 新值”；确认前不产生节点，确认后日期/进度与甘特图一致。
- 对未知参数或不支持的操作明确返回错误；日期未提供时不要暗示已完成具体排期。
- 新工具同时使用 R-01 的修订保护，验证重复确认、拒绝、旧草稿、审批后续跑都不会重复建档或覆盖新计划。

证据：[草稿参数和落盘字段](retest-evidence-agent-planning-2026-10-21/deep-results.json)、[甘特图实际节点](retest-evidence-agent-planning-2026-10-21/agent-plan-fields-missing-wide.jpg)。

| 9 | 再考虑依赖和批量排期 | 有实际需求后增加前置节点、阻塞原因与批量顺延；先预览受影响节点再确认，不自动改动已完成节点或制造日期冲突 |

### 并发保护契约

`revision` 是原文档文本的 SHA-256，覆盖排期元数据、项目关联、状态和正文；不会因同秒修改或正文未变而漏检。`indexer.update_doc()` 在原有 `mutation_lock` 和索引写锁内完成读取、版本比较与写入；同步应用也使用该变更锁。修订号只作为接口返回值，不写入文档元数据。

甘特图和里程碑文档编辑器保存时携带所读取的修订号，例如：

```json
{"expected_revision":"读取接口返回的 revision","progress":64.5}
```

冲突响应为 `409/revision_conflict`，携带 `current` 供比较。冲突后不会自动重试覆盖；甘特图中的“载入当前值并合并我的修改”将当前记录作为新基线，保留用户实际改动，用户核对后再次保存。同步界面刷新保留脏表单；保存期间继续键入的文档修改使用上一次成功保存的新修订号。

为兼容已有调用方，普通 `/api/docs/<id>` 写接口仍接受未带修订号的旧请求；需要并发保护的调用方必须传 `expected_revision`。当前甘特图、已有里程碑文档编辑器及 Agent 排期更新均使用此保护。Agent 生成或确认排期/状态/项目更新草稿时缺少修订号会明确拒绝；旧草稿确认时若文档变化，草稿执行失败并保留当前计划，需重新读取后生成新草稿。

### 状态与 Agent 排期规则

- `完成/已完成` → `done`；`受阻/阻塞` → `blocked`；`进行中` → `active`。未识别的自定义状态 → `planned`，计为待完成，保留原始显示标签。完成别名在完成数、待完成数和图表逾期判断中一致。
- `kb_read` 返回开始/截止、进度、状态、项目、分类及完整 `revision`；原有正文 `version` 保留，用于正文替换和撤销。
- `kb_create_entry(kind=milestone)` 支持 `start_date/due/progress/status/projects`；未提供日期时明确保持待排期，不默认排到当天。
- `kb_update_entry` 只发送实际修改字段，省略 `body` 保留正文；修改排期/状态/项目必须提供读取到的 `expected_revision`。正文覆盖仍需要原有 `expected_version`，追加和撤销保护保留。
- 两个写工具对未知参数、错误类型和不支持的排期操作明确报错。非法日期、倒置日期、非法进度在生成草稿前拒绝，不写入计划或活动。
- 主聊天、悬浮助手和任务面板的草稿预览显示字段“旧值 → 新值”，并保留新建条目的正文预览。确认前不建节点，拒绝不写入；重复确认拒绝，确认后原任务可继续，不重复追加用户问题或建档。
