### FR-01：迁移 PDF 时可能打开另一份文件

位置：[app/literature.py](../app/literature.py)，`set_pdf_dir()` 第 493–507 行，尤其是第 503–505 行；读取路径选择见 `_item_pdf_path()` 第 703–712 行。

复现：

1. 导入一份四页合成 PDF，记录下载内容哈希。
2. 在新的存储目录中放入另一份一页 PDF，文件名与该文献的 `stored_filename` 完全相同。
3. 调用 `/api/literature/storage`，指定新目录并开启 `move_existing`。
4. 再请求原文献的 `/api/literature/<id>/pdf`。

实际：迁移跳过同名文件，但全局 PDF 目录已经切换；读取器优先使用新目录下的同名文件。下载哈希从 `65766b14…7bb53` 变为 `3de2b378…710b`，原文献因此打开另一份 PDF。原文件仍保留在旧目录，本轮未发生物理覆盖；问题是文献身份与内容发生静默错配。

建议：迁移前完成全量冲突检查；相同内容可以复用，不同内容应拒绝迁移或生成新文件名并同步更新对应关系。文件与元数据准备成功后再切换配置，失败时保留原来的可用状态。

验收：空目标目录、同名同内容、同名不同内容、目标无写权限、迁移中断分别验证。所有成功迁移的文献，其前后下载哈希必须一致；不能只断言 HTTP 200 或文件数量。

### FR-02：两个文献信息窗口会互相覆盖已保存字段

位置：[web/literature.js](../web/literature.js)，`infoPayload()` 第 13–16 行、`saveInfo()` 第 690–695 行；[app/literature.py](../app/literature.py)，`update_item()` 第 212–257 行。

复现：两个页面同时打开同一文献，初始题名为 `audit`。窗口 A 将题名改为“窗口 A 已保存的新题名”并保存；窗口 B 只改作者后保存。

实际：两个页面均显示“信息已保存”。后端回读的作者是 B 的新作者，但题名回退成 `audit`。B 提交了整份旧表单，文献信息接口没有检查读取时的修订号。

这与普通笔记和文献正文笔记不同：本轮同时验证了它们的过期修订拒绝逻辑，均能阻止旧内容覆盖。

建议：信息编辑器保存读取时的版本，服务端原子检查版本；只提交实际修改字段。冲突时保留用户输入，并提供重新加载或合并路径。阅读进度自动保存也应避免回写过期的阅读状态。

验收：A 修改题名、B 修改作者时，两项修改均保留，或 B 得到明确冲突提示；两个窗口修改同一字段时不得静默覆盖。对导入文献和 `entry-*` 文献都验证。

证据：[覆盖后的界面](review-evidence-2026-10-26/metadata-stale-overwrite.png)、[浏览器结果](review-evidence-2026-10-26/supplemental-ui-results.json)。

### FR-03：批注意见没有纳入草稿保存保护

位置：[web/literature.js](../web/literature.js)，`dirty()` 第 19 行、`guard()` 第 20–24 行、`switchTab()` 第 623 行，以及 `annList()` 第 720–734 行。

复现：打开已有批注，在“批注”文本框输入新意见；不点击保存，切换到“信息”，再回到“批注”并打开该记录。

实际：新意见消失，编辑框恢复旧的已保存文字。输入新意见时 `ERWLiterature.dirty()` 仍返回 false；当前保存保护只检查文献信息和阅读笔记。相同批注点击“保存批注”可以正常持久化，说明缺陷集中在草稿与离开保护。

建议：按文献和批注 ID 保存编辑草稿；页签切换、切换批注、切换文献及离开页面均应保留草稿或触发保存/丢弃/取消选择。保存失败也必须保留意见。

验收：上述离开场景、显式保存、保存失败、取消离开都覆盖，并与窗口关闭时的未保存检查保持一致。

证据：[切换前](review-evidence-2026-10-26/annotation-before-switch.png)、[切换后](review-evidence-2026-10-26/annotation-after-switch.png)。截图中央为空白是本轮四页合成 PDF 的设计，不是渲染缺陷。

### FR-04：PDF 迁移成功但 Markdown 仍指向旧路径

位置：[app/literature.py](../app/literature.py)，`set_pdf_dir()` 第 497–529 行；路径存在性检查见 [app/store.py](../app/store.py) 第 491–505 行。

复现：导入 PDF 后，通过设置接口迁移到 `RelocatedPDFs`。本轮响应为 `ok: true, moved: 2, skipped: 0, updated: 0`。

实际：文件已搬走，文档的 `attachment` 仍为 `Knowledge/Literature/PDF/<filename>`，`/api/docs/<doc_id>/attachment` 返回 404。文献阅读器自己的 `/api/literature/<paper_id>/pdf` 仍返回 200，因为它通过新目录和 registry 文件名查找；仅检查阅读器会漏掉问题。

原因：迁移先移动文件，随后用要求文件真实存在的 `store.resolve_attachment(doc)` 解析旧路径；文件已不在旧位置，返回 None，路径更新被跳过。

建议：移动前收集旧路径到新路径的映射及所有引用者，迁移后按映射更新，不再依赖旧文件存在。应与 FR-01 一起设计失败恢复。

验收：迁移后 Markdown 中路径真实存在，文档附件接口和文献阅读器均返回原内容，重建索引后仍成立。

### FR-05：重建一个共享 PDF 的关联会破坏另一个引用

位置：[app/literature.py](../app/literature.py)，`rebuild_registry()` 第 398–410 行及第 439–447 行。

复现：两篇有效文献的 `attachment` 都指向 Workspace 中同一个 `shared.pdf`，对其中一篇执行 `/api/literature/rebuild`。

实际：重建把文件移入统一 PDF 目录，仅更新当前文档的附件路径；另一篇文献的 `pdf_available` 由 true 变为 false。两篇文献本来都可以正常读取同一个文件。

建议：处理共享附件时保留原文件，或更新全部引用者；明确附件共享与删除规则，避免只修复当前条目。

验收：单篇重建和全量重建后，两篇文献都能读取原 PDF；重复重建不新增孤立副本，也不破坏现有引用。

### FR-06：直接附件文献的阅读位置不持久化

位置：[app/literature.py](../app/literature.py)，`_document_item()` 第 97–101 行、`update_item()` 第 220–224 行；前端保存调用见 [web/literature.js](../web/literature.js) 第 493 行。

复现：创建一篇 Markdown 文献，`attachment` 指向真实存在的四页 PDF；文献详情接口返回可读的 `entry-<doc_id>`。向该文献保存 `last_page: 3, page_count: 4` 后重新读取。

实际：接口返回成功，但 `last_page` 仍为 1。未登记的 `entry-*` 更新分支仅写 Markdown 元数据白名单，忽略阅读位置；重新构造条目时又固定初始化成第一页。

建议：为直接附件路径建立稳定的阅读状态存储，或在首次打开时安全登记，并保留文档身份和附件引用。

验收：直接附件、导入 PDF、给旧文献补充 PDF 三条路径都能在离开、刷新和重启后恢复阅读页码。

### FR-07：项目更新校验失败前已发生改名

位置：[app/projects.py](../app/projects.py)，`update_project()` 第 340–359 行。

复现：创建“校验前项目”及关联笔记，提交项目更新 `{"name":"不应生效的改名","status":"INVALID"}`。

实际：HTTP 返回 400，但旧目录已不存在，关联笔记的项目名称也已经变成“不应生效的改名”。非法状态的验证发生在移动目录和重写关联之后；registry 的最终保存没有执行，可能留下目录、文档、registry 不一致的状态。

正常项目改名和删除联动在本轮通过。此问题的直接触发点是非法 API 输入；正常页面的状态下拉框不会主动生成 `INVALID`，因此不将它表述为正常改名必现故障。

建议：先验证整个更新请求，再开始任何写入；多文件修改失败应报告部分完成或恢复原状态，不能返回普通校验失败却留下改动。

验收：无效状态、冲突名称、无效简称和文件操作失败时，目录、registry、关联文档、待办及索引保持一致。

### FR-08：Markdown 取消置顶没有清除文献收藏

位置：[app/literature.py](../app/literature.py)，`_apply_doc_meta()` 第 152–153 行。

复现：通过文献信息设置收藏为 true，然后通过文档接口将 Markdown `pinned` 改为 false，重新读取文献。

实际：Markdown 为 false，文献 `favorite` 仍为 true。映射使用 `bool(doc['pinned'] or item.get('favorite'))`，旧值为 true 时无法被明确的 false 覆盖。

建议：`pinned` 字段存在时，以该值为准；仅字段缺失时兼容旧 registry 值。

验收：两个入口执行 true→false 和 false→true 后，列表星标、复选框与 Markdown 一致。
